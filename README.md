# Minibox - учебный контейнерный runtime на C++17

`Linux` / `WSL Ubuntu`, запуск от обычного пользователя. Проверено в `WSL Ubuntu` с `UID 1000`.

## Сборка и запуск

В терминале Ubuntu перейдите в каталог проекта. Нужны `g++`, `make`, `Python 3`, `tar`.

```sh
make
python3 rootfs.py
./runtime daemon
./runtime run "$HOME/minibox-rootfs" /bin/sh
```

[rootfs.py](/rootfs.py) скачивает фиксированный `Alpine 3.20.3` с официального зеркала и проверяет SHA256. Это тестовый образ. Храните rootfs в файловой системе `Linux`, например в домашнем каталоге `WSL`, а не на `/mnt/c`. Распаковка требует пустого каталога; владельцы файлов остаются текущим пользователем.

```sh
./runtime run -d "$HOME/minibox-rootfs" /bin/sh
./runtime list
./runtime attach PID
./runtime logs PID
./runtime logs -f PID
./runtime kill PID
make test
```

Вместо `PID` подставьте число, напечатанное `run -d`. Для тестирования другой rootfs: `ROOTFS=/path/to/rootfs make test`.

## CLI

* `daemon` - запустить фоновый демон текущего пользователя.
* `run [-d] [--overlay] [--network PID] ROOTFS COMMAND [ARGS...]` - запустить процесс, без `-d` подключить терминал и вернуть `exit code` команды. Ошибки настройки изоляции возвращают `125`.
* `list` - показать PID управляющего процесса и состояние всех контейнеров текущего демона, включая завершённые.
* `logs [-f] PID` - прочитать объединённые `stdout/stderr`, `-f` продолжает читать до закрытия `PTY`.
* `attach PID` - подключить ввод и вывод существующего `PTY`. `Ctrl+]` отключает клиента. `Ctrl+C` передаётся в `PTY` как управляющий символ.
* `kill PID` - отправить `SIGTERM PID 1` контейнера, через три секунды `SIGKILL`, если он ещё работает. Команда подтверждает запрос, завершение видно в `list`.

## Архитектура

Один процесс демона обслуживает `Unix socket` и `PTY` через `poll`. `forkpty` создаёт управляющий процесс контейнера с терминалом; он создаёт `user namespace`, отображает `UID/GID` пользователя в `0` и запрещает `setgroups`. Затем создаёт `PID`, `mount`, `UTS`, `IPC` и `network namespaces`. В новом сетевом пространстве поднят `loopback`; внешняя сеть отсутствует.

`Mount propagation` переключается в `private`; `rootfs` становится корнем через `chroot. /dev - tmpfs`, базовые устройства привязываются с хоста, `/dev/pts` - отдельный `devpts`. Сохранённые дескрипторы хоста закрываются до `exec`. После `fork` команда получает `PID 1` и собственный `/proc`. Управляющий процесс ждёт команду и сохраняет её статус. `PID` в `CLI` - `PID` этого управляющего процесса в пространстве хоста.

Сокет и файлы логов находятся в `$XDG_RUNTIME_DIR/minibox-UID`, при отсутствии переменной - `/tmp/minibox-UID`. `umask 0077` ограничивает доступ. Логи сохраняются как `PID.log`; список контейнеров хранится в памяти демона.

## Протокол

Один Unix stream socket на запрос. Первая строка - имя команды. Для `run` следующая строка содержит количество аргументов, далее каждый аргумент отдельной строкой; `rootfs` передаётся абсолютным путём. Ответ - `PID` и перевод строки. Переводы строк внутри аргументов не поддерживаются. Для остальных команд, кроме `list`, следующая строка - `PID`.

`list`, `logs`, `kill` и внутренняя команда `wait` возвращают текст и закрывают соединение. `wait` возвращает `-1`, пока контейнер работает, либо код завершения. `attach` переключает соединение в двунаправленный поток байтов `PTY`; `follow` сначала отдаёт накопленный лог, затем поток. Клиент переводит локальный терминал в `raw mode` и восстанавливает его при штатном выходе. Вывод терминала может содержать `CRLF` и `ANSI-последовательности`. Несколько клиентов могут подключиться одновременно и разделяют терминал.

## OverlayFS

```sh
./runtime run --overlay "$HOME/minibox-rootfs" /bin/sh
```

Флаг `--overlay` подключает исходную `rootfs` как нижний слой. Изменения и удаления
попадают в отдельный верхний слой каждого контейнера; исходные файлы не изменяются.
Новый запуск получает новый пустой верхний слой. Без флага сохраняется прежний режим
прямой записи в `rootfs`.

Демон передаёт создание слоя управляющему процессу. Он создаёт уникальный каталог
`layers-XXXXXX` внутри каталога состояния, с подкаталогами `upper`, `work`, `merged`.
Overlay монтируется только в mount namespace контейнера с параметром `userxattr`.
Файл `PID.layer` содержит путь к слою. После выхода процессов монтирование исчезает;
`upper`, `work` и файл метаданных сохраняются для анализа изменений. Автоматического
удаления сохранённых слоёв и повторного запуска поверх существующего слоя нет.

Нужны поддержка `rootless OverlayFS` ядром и подходящая файловая система для `upper/work`
(например `ext4` в `WSL`). Не размещайте каталог состояния на Windows-диске `/mnt/c`.
В путях `OverlayFS` запрещены запятая, двоеточие и обратная косая черта из-за формата
параметров `mount`. `Rootfs` следует считать неизменяемой на хосте во время работы `overlay`.
При ошибке `mount runtime` завершает запуск с ошибкой; скрытого перехода к прямой записи нет.

## Общая сеть

`--network PID` принимает `PID` работающего контейнера **этого демона**, напечатанный
`run -d` или `list`. Произвольные `PID` процессов хоста не принимаются.

Пример `TCP` echo-сервера на средствах тестовой Alpine:

```sh
server=$(./runtime run -d --overlay "$HOME/minibox-rootfs" /bin/sh -c \
  'exec nc -ll -p 18080 -e /bin/cat')

./runtime run --overlay --network "$server" "$HOME/minibox-rootfs" /bin/sh -c \
  'printf NETWORK_OK | nc -w 1 127.0.0.1 18080'

./runtime kill "$server"
```

## Проверки и ограничения

Автотесты [tests.py](/tests.py) проверяют вывод команды, `PID 1`, `exit code`, `detached`, `list`, `logs`, `follow`, `kill` и двунаправленный `attach`. Они требуют разрешённых `unprivileged user namespaces` в ядре и политике `Ubuntu`.

`make test` самостоятельно создаёт отдельный каталог состояния и новый демон,
останавливает тестовые контейнеры и демон, удаляет временные данные. Существующие
пользовательские контейнеры не затрагиваются. Тесты работают без sudo; нужны Python 3,
тестовая Alpine rootfs, namespaces и rootless OverlayFS. Отсутствие возможностей
считается ошибкой теста, а не незаметным пропуском.

Проверяются:

* вывод, PID 1, exit code и detached;
* list, logs и новый вывод после подписки follow;
* выполнение команды через attach, без ложного успеха на эхе введённой строки;
* корректный SIGTERM с кодом 0 и принудительный SIGKILL с кодом 137;
* OverlayFS copy-up, удаление нижнего файла и неизменность lowerdir;
* отдельные верхние слои одновременных контейнеров;
* реальный TCP-обмен через общую сеть и недоступность сервера из отдельной сети;
* совпадение user/net и различие mount/UTS/IPC/PID namespaces;
* жизнь участника после остановки владельца сети и отклонение неверных/завершённых PID.

Это учебная реализация, не граница безопасности для недоверенного кода. Нет `cgroups`, `seccomp`, ограничения `capabilities`, ротации логов, восстановления состояния после перезапуска, передачи изменения размеров окна. Без `--overlay rootfs` изменяется напрямую; для независимых изменений используйте `--overlay`. `PID 1` должен самостоятельно обрабатывать сигналы и собирать дочерние процессы. Медленный читатель может задержать цикл демона. При аварийном завершении клиента raw mode может потребовать `stty sane`.
